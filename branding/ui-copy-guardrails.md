# UI Copy Guardrails

세 사이트의 UI 문구는 장식보다 사용 흐름을 우선한다. 화면에 남기는 텍스트는 사용자가 지금 무엇을 볼지, 무엇을 할지, 왜 막혔는지 판단하는 데 직접 도움을 줘야 한다.

## 장식성 텍스트 기준

다음 중 하나에 해당하지 않는 문구는 추가하지 않는다.

- 현재 위치나 화면의 역할을 알려준다.
- 사용 가능한 행동이나 다음 선택지를 알려준다.
- 게임 상태, 오류, 제한, 성공 여부를 알려준다.
- 프로젝트의 실제 맥락이나 접근 가능한 링크를 설명한다.
- 규칙 이해에 필요한 카드게임 용어를 짧게 보강한다.

삭제 후보는 다음과 같다.

- 같은 정보를 다른 표면에서 이미 보여주는 상태 배지
- 분위기만 만드는 영문 라벨, 슬로건, 키커
- 클릭 가능한 요소처럼 보이지만 행동이 없는 장식 문구
- 한국어 줄바꿈을 망가뜨리는 긴 복합 명사
- 캔버스나 카드 텍스트를 가리는 상시 설명 패널

## 앱별 적용

### site

- 웹에서 직접 접근 가능한 프로젝트와 작업 맥락을 먼저 보여준다.
- 포트폴리오 문구는 자기소개보다 프로젝트 인덱스, 데모 진입, 작업 증거를 우선한다.
- 애니메이션과 레이아웃은 기술 시연이 될 수 있지만, 문구는 짧고 검증 가능해야 한다.
- 임의 색상이나 장식 도형은 먼저 `brand-context.md` 또는 `site-direction.md`에 의도를 남긴 뒤 적용한다.

#### 포트폴리오 문체

포트폴리오 문구는 발표 대본이나 자기소개서가 아니라, 채용자와 협업자가 빠르게 검증할 수 있는 작업 메모에 가깝게 쓴다.

- 첫 문장은 프로젝트의 성격과 직접 구현한 범위를 말한다.
- 두 번째 정보는 기술, 화면, 배포 링크처럼 확인 가능한 증거를 둔다.
- "경험했습니다", "도전했습니다", "가능성을 탐구했습니다"처럼 결과를 흐리는 표현은 쓰지 않는다.
- "흐름", "구조", "시스템", "인터랙션" 같은 넓은 단어는 실제 화면명이나 기능명으로 바꾼다.
- 템플릿처럼 보이는 균형 잡힌 수식어보다, 거칠어도 구체적인 구현 사실을 우선한다.

권장 문장 구조는 다음과 같다.

- `문제/목표`: 무엇을 만들거나 고쳤는가.
- `작업`: 어떤 화면, 기능, 기술을 직접 연결했는가.
- `증거`: 웹 링크, 레포, 빌드, 화면 흐름으로 무엇을 확인할 수 있는가.

### NULSIGHT

- 룰은 NULSIGHT 고유 규칙을 기준으로 한다.
- YGOPRO는 `field`, `hand`, `grave`, `banish`, `chain/stack`, `selectable/selected card` 같은 TCG UI 어휘와 피드백 구조만 참고한다.
- COMMAND에는 지금 가능한 행동, 우선권, 타이밍처럼 조작 판단에 필요한 항목만 둔다.
- 존 순서, 계정, 정렬, 접속 상태처럼 이미 화면 구조나 서버 응답으로 알 수 있는 정보는 반복 노출하지 않는다.
- 카드 상세와 효과 선택은 카드 텍스트 가독성을 우선하고, 플레이필드를 장시간 덮는 장식 문구를 넣지 않는다.

## 작성 체크리스트

새 문구나 UI 라벨을 넣기 전에 아래를 확인한다.

1. 이 문구를 지워도 사용자가 같은 결정을 할 수 있다면 삭제한다.
2. 같은 뜻의 문구가 한 화면에 두 번 나오면 하나만 남긴다.
3. 모바일 폭에서 한국어 음절 단위로 찢어지면 더 짧은 표현으로 바꾼다.
4. 제목은 명사구, 설명은 한 문장, 버튼은 동사형으로 끝낸다.
5. 영어 키커는 화면 구조상 꼭 필요할 때만 쓰고, 기능 라벨은 한국어를 우선한다.
6. 한 섹션에서 키커, 제목, 설명, 보조 설명이 모두 필요한지 의심한다. 대부분은 제목과 한 문장이면 충분하다.
7. 버튼 라벨은 가능하면 2-5음절의 한국어 동사형 또는 명확한 명사형으로 유지한다.
8. 카드/오버레이 안의 설명 문단은 두 줄을 넘기기 전에 줄일 방법을 먼저 찾는다.
9. 포트폴리오 카드의 설명은 "했다/구현했다/연결했다/정리했다"처럼 작업 주체가 보이는 동사로 끝낸다.
10. 기술 태그는 실제로 레포나 화면에서 확인 가능한 것만 둔다.
11. 추상 명사 두 개가 이어지면 하나는 화면명이나 기능명으로 바꾼다.

## 화면 밀도 기준

- site: 프로젝트 링크와 구현 증거가 우선이다. 장식 문구가 프로젝트 카드보다 먼저 읽히면 실패다.
- NULSIGHT: 듀얼 중에는 카드, 선택 가능 여부, 현재 행동, 스택/효과 처리가 장식보다 우선한다.
- 모든 앱: 같은 상태가 헤더, 본문, 푸터에 반복되면 하나만 남긴다.

## 구조와 상태 표현 기준

- 강한 문구보다 강한 구조를 먼저 쓴다.
- 장식 표식은 상태나 상호작용 의미가 있을 때만 쓴다.
- 절제는 짧은 문구, 좁은 팔레트, 선명한 상태 신호로 해석한다.
- 구조적 스타일은 거친 말투가 아니라 노출된 레이아웃과 명확한 조작감으로 해석한다.
- 첫 화면은 자기소개보다 프로젝트 접근과 실제 작업 증거를 먼저 보여준다.

## 검증 기준

- 데스크톱과 모바일 스크린샷에서 최상위 제목이 어색하게 쪼개지지 않는다.
- 카드 이름과 효과 텍스트가 버튼, 배지, 장식 요소보다 먼저 읽힌다.
- 게임 화면의 중앙 플레이필드가 상시 UI에 의해 가려지지 않는다.
- 같이가계, NULSIGHT, site 모두 같은 줄바꿈 원칙과 간결한 문구 기준을 공유한다.
